## Findings

### F-1 — Firewall posture check fails with ufw on a legacy-iptables host (false negative)

**Observed:** this PC, ufw `active` with `DEFAULT_INPUT_POLICY="DROP"`; the client reports
`linux.firewall.active: FAIL: nftables present but no default-deny input chain`, so an ENFORCE profile requiring
the firewall refuses a correctly protected device.

**Cause (from source and host):** `iptables v1.8.10 (legacy)` — ufw's rules live in legacy xtables, not in the
nftables ruleset. The daemon has `CAP_NET_ADMIN` (`AmbientCapabilities=cap_net_admin`), so `nft -j list ruleset`
succeeds and `collect_firewall` (`client/src/posture.rs:271`) returns FAIL at the nft step without trying the
iptables or ufw backends. The early return predates #149; before #149, the text match on `policy drop` passed this
host only by accident (Docker's forward chain). Note the fallbacks may not help as is: `ufw status` needs root and
legacy `iptables -L` needs `CAP_NET_RAW`, which the unit does not grant.

**Impact:** a real user on a distro or host using iptables-legacy (older Debian/Ubuntu, RHEL 7, hosts switched to
legacy for Docker) with ufw/iptables default-deny is refused any resource whose profile requires the firewall.
Medium. Not a security hole (fails closed).

**Probe (as the daemon's user with only `CAP_NET_ADMIN`, via `systemd-run`):** `iptables -L INPUT` → `can't open lock
file /run/xtables.lock: Permission denied`; `ufw status` → `You need to be root`. So reordering the fallbacks alone
can't fix it.

**Status: FIXED** (branch `fix/e2e-live-findings`; user decision: ufw config fallback, iptables-legacy hosts only).
Details: `Sprint15/Member2-Rust-Client/Phase1-Proto-and-Linux-Collectors.md` → Post-Phase Fixes.
