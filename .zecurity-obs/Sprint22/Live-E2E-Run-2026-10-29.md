## Findings

### F-1 — Firewall posture check fails with ufw on a legacy-iptables host (false negative)

**Observed:** this PC, ufw `active` with `DEFAULT_INPUT_POLICY="DROP"`; the client reports
`linux.firewall.active: FAIL: nftables present but no default-deny input chain`, so an ENFORCE profile requiring
the firewall refuses a correctly protected device.

**Cause (from source and host):** `iptables v1.8.10 (legacy)` — ufw's rules live in legacy xtables, not in the
nftables ruleset. The daemon has `CAP_NET_ADMIN` (`AmbientCapabilities=cap_net_admin`), so `nft -j list ruleset`
succeeds and `collect_firewall` (`client/src/posture.rs:271`) returns FAIL at the nft step without trying the
iptables or ufw backends. The early return predates #149; before #149, the text match on `policy drop` passed this
host only by accident (Docker's forward chain). Note the fallbacks may not help as is: `ufw status` needs root and
legacy `iptables -L` needs `CAP_NET_RAW`, which the unit does not grant.

**Impact:** a real user on a distro or host using iptables-legacy (older Debian/Ubuntu, RHEL 7, hosts switched to
legacy for Docker) with ufw/iptables default-deny is refused any resource whose profile requires the firewall.
Medium. Not a security hole (fails closed).

**Probe (as the daemon's user with only `CAP_NET_ADMIN`, via `systemd-run`):** `iptables -L INPUT` → `can't open lock
file /run/xtables.lock: Permission denied`; `ufw status` → `You need to be root`. So reordering the fallbacks alone
can't fix it.

**Status: FIXED** (branch `fix/e2e-live-findings`; user decision: ufw config fallback, iptables-legacy hosts only).
Details: `Sprint15/Member2-Rust-Client/Phase1-Proto-and-Linux-Collectors.md` → Post-Phase Fixes.

### F-2 — A steadily slow reader is cut after a few seconds

**Observed:** downloads of `big.bin` through the tunnel with `curl --limit-rate`:

| Reader | Result |
|---|---|
| 25 KB/s, ~14 min download | connector `ending the session … reason="device stalled with its tunnel queue full"` **2.3 s** after start; curl drained the ~3.7 MB already buffered and failed at 144 s (exit 18). Reproduced: 2.8 s / 134 s |
| 25 KB/s, 12 s runs (×2) | ended after 9.9 s and 6.5 s |
| 50 KB/s, 100 KB/s, 500 KB/s, 2 MB/s, 12 s runs | not ended |
| 500 KB/s with a 5 s `SIGSTOP` pause | **not** ended, full 20 MB, exit 0 |

**Cause (from source):** `connector/src/agent_tunnel.rs` `DEVICE_STALL_LIMIT = 2 s` (Sprint 20 Fix 14, F48): a Shield
chunk waits at most 2 s for room in the device's full tunnel queue, then the session ends — an accepted limit
(user, 2026-10-26) because all tunnels of a shield share one Control stream; per-tunnel flow control (a proto change)
is the recorded follow-up. The decision's wording is "ends only when it makes no progress for 2 s"; a steady 25 KB/s
reader is making progress but is still cut (inferred: its window opens in bursts more than 2 s apart once the
client-side buffers are full).

**Impact:** a real user on a slow link (≤ ~25 KB/s sustained, e.g. a poor mobile connection) loses long downloads or
streams. Medium. Fix belongs to the per-tunnel flow-control follow-up.

### F-3 — A connector restart cuts access for up to a client sync interval even with a healthy peer connector

**Observed:** A restarted at 07:14:55; A refused new QUIC connections while stopping → client tried B → B answered
`SHIELD_NOT_ATTACHED` (shield still on A) → client `early transport resync` at 07:14:56.37 picked up a snapshot
taken while A was marked disconnected (`goodbye sent: the controller marked this connector disconnected`), so its
map held only B → every later attempt: `no connector accepted tunnel (auth/denial only) — failing closed, no
resync`. A served again at 07:14:56.57 (`connector authorized — data plane open`) and had the shield at 07:14:58.3,
but received **no** client attempt until the client's 60 s background sync at 07:15:29.

**Cause (from source):** `client/src/net_stack.rs` ~1556–1600: `SHIELD_NOT_ATTACHED` is not counted as a transport
failure, so when no connector accepts, the client fails closed **without** signalling a resync ("re-polling won't
help", finding #8). That is right for auth denials but not for a shield that is moving between connectors. Related
to FU-8 (clients learn changes on a 60 s poll).

**Impact:** every connector restart (upgrade, auto-update, reboot) can cut users of that connector's resources for up
to 60 s, even when another connector is healthy. Medium.

**Suggested fix:** treat `SHIELD_NOT_ATTACHED` as transport-class (signal a rate-limited resync), so the client
re-fetches the transport map within seconds while the shield re-homes.

### F-4 — Getting back in after a device revoke fails and leaves orphan devices

**Observed:** after the admin revoked the device, the daemon exited (exit 0, so `Restart=on-failure` didn't restart
it). `zecurity-client login` then ran the browser flow and enrolment (`Generating device certificate...`) and failed:
`daemon could not be started — run: systemctl status zecurity-client … No such file or directory`, exit 1. Starting the
service (`sudo systemctl start zecurity-client`) didn't help: the daemon loaded the saved revoked state, re-checked,
logged `device revoked — exiting` and stopped again, so the next `login` failed the same way. Each failed `login`
left a new **active** device on the server whose key the client never saved (`415e9d0f…` 09:27:02, `d09a71e4…`
09:29:58; revoked by the admin afterwards). Only `logout` (clears the state) → start the service → `login` worked.

**Cause (from source and logs):** `client/src/daemon.rs` exits on `DirectiveRevoked` (5009, 5186) and the durable
state keeps the revoked device; startup reloads it, the controller says revoked, exit again. `login` enrols the
device before it reaches the daemon (`ipc::ensure_daemon_and_send`).

**Impact:** a user whose device was revoked by mistake, or who is let back in, can't sign in with the documented
command; every attempt adds an orphan active device. `status` says only `Revoked — contact your admin`. Medium.

**Suggested fix:** on a revoke the daemon should clear the revoked workspace state (keep only a marker for `status`)
and not exit, or exit non-zero so systemd restarts it; and `login` should reach the daemon before enrolling (and
clear a revoked state itself).
