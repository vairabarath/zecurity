# Phase 1 — Proto + Linux Collectors

> Depends on nothing — Day 1. **Land this first**: M1 and M3 do not overlap with M2's
> files, so this phase should not become a bottleneck, but the generated stubs are a
> prerequisite for M1-D and any future connector-side posture awareness.

## Goal

Define the wire format for posture reporting and implement Linux-only collection with
strict normalization.

## Files

| File | Change |
|------|--------|
| `proto/client/v1/client.proto` | `ReportDevicePostureRequest`/`ReportDevicePostureResponse` wrapper messages (the RPC's actual signature — see below for why a bare `DevicePostureReport` can't authenticate) + `DevicePostureReport`/`PostureCheck` messages + the `ReportDevicePosture` RPC |
| `client/src/posture.rs` | **new** — Linux collectors + normalization |

## proto/client/v1/client.proto

The RPC must authenticate the same way `GetACLSnapshot` does — a bare
`DevicePostureReport` cannot authenticate on its own (access tokens carry no device
claim; see M1 Phase 2). Wrap it in a request message that mirrors
`GetACLSnapshotRequest`'s `{access_token, device_id}` shape:

```protobuf
message ReportDevicePostureRequest {
  string access_token = 1;
  string device_id    = 2;
  DevicePostureReport report = 3;
}

message ReportDevicePostureResponse {
  bool accepted = 1;
  string rejection_reason = 2;  // empty if accepted
}

message DevicePostureReport {
  string report_id      = 1;  // client-generated UUID, idempotency key
  int64  reported_at    = 2;  // unix epoch seconds, client clock
  string client_version = 3;
  string os_name        = 4;
  string os_version     = 5;
  repeated PostureCheck checks = 6;
}

message PostureCheck {
  string check_id = 1;   // registered ID, e.g. "linux.disk_encryption.luks"
  CheckStatus status = 2;
  string detail = 3;     // short human string, never raw command output
}

enum CheckStatus {
  CHECK_STATUS_UNSPECIFIED = 0;
  PASS = 1;
  FAIL = 2;
  UNSUPPORTED = 3;
  UNKNOWN = 4;
  ERROR = 5;
}

service ClientService {
  rpc ReportDevicePosture(ReportDevicePostureRequest) returns (ReportDevicePostureResponse);
}
```

**`reported_at` is a plain `int64` unix-epoch-seconds field, not
`google.protobuf.Timestamp`.** No existing `.proto` file in this repo uses `Timestamp`,
and `client/Cargo.toml` does not currently declare `prost-types` (required for
`Timestamp` support in the generated Rust code) — adding it is an extra dependency this
sprint doesn't need when a plain `int64` does the job with zero new tooling.

**Never change existing field numbers on this file** (per `CLAUDE.md` proto rule) —
these are new messages/RPC, additive only.

**Generation is two separate steps, not one `buf generate`:**
- `buf.gen.yaml` only configures the Go plugins — running `buf generate` from the repo
  root regenerates the **Go** stubs only.
- Rust stubs are generated by `client/build.rs` (`tonic_build::configure().compile_protos(...)`),
  which runs automatically as part of `cargo build`. There is no separate Rust
  generation command to remember — just build the client crate.
- Run both (`buf generate` then `cd client && cargo build`) and commit all regenerated
  output in the same commit as the `.proto` change.

## client/src/posture.rs

Registered check IDs (v1, Linux only):

- `linux.os.version` — OS/version.
- `linux.disk_encryption.luks` — LUKS full-disk encryption present and unlocked.
- `linux.firewall.active` — a firewall (nftables/iptables/ufw) is active with a default-deny or equivalent posture.
- `linux.secure_boot.enabled` — Secure Boot enabled. **Note: Secure Boot does not
  require a TPM** — it's a firmware/UEFI feature checked via `efivars`
  (`/sys/firmware/efi/efivars/SecureBoot-...`), independent of TPM presence. Report
  `UNSUPPORTED` for non-UEFI (legacy BIOS) systems, not for TPM absence.

Each collector:

- Runs as its **own isolated tokio task** with its **own timeout** — isolation matters
  because a bare `tokio::time::timeout` around an `.await` does **not** catch a panic;
  only running the collector in its own spawned task and handling that task's
  `JoinError` (panic vs. timeout vs. clean return) reliably prevents one bad collector
  from taking down report assembly.
- Returns one of `PASS/FAIL/UNSUPPORTED/UNKNOWN/ERROR` — `UNSUPPORTED` for a check that
  doesn't apply to this environment (e.g. legacy BIOS for Secure Boot), `ERROR` for a
  collector that failed to run (permissions, missing binary, panicked, or timed out),
  `UNKNOWN` only when the result is genuinely indeterminate.
- Returns a short `detail` string for operator visibility — **never** raw command
  stdout/stderr (avoids leaking system info via GraphQL visibility in M1-E1).

## Tests

- Unit: each collector against a mocked/faked environment for every possible status.
- Unit: a collector that **panics** inside its spawned task is caught via `JoinError` and
  recorded as `ERROR` — this must be tested by making a collector panic, not just sleep
  past a timeout, since those are different failure modes and a timeout alone does not
  prove panic-safety.
- Unit: a collector that hangs past its timeout is treated as `ERROR` and doesn't block
  report assembly — the other checks still populate the report.

## Post-Phase Fixes

### Fix: the firewall check passed on any `policy drop`, not only the inbound chain (2026-10-28, `c7d812cb`)
**File:** `client/src/posture.rs` `collect_firewall` (+ tests in `client/src/posture_tests.rs`).

**Issue:**
- The nftables branch matched the text `policy drop` / `policy reject` anywhere in `nft list ruleset`.
- A drop policy on a **forward** or **output** chain (Docker's `FORWARD`, or any tool's) therefore reported `linux.firewall.active` = PASS while inbound was wide open.
- **Found live 2026-10-28:**
  1. This PC had only `table inet fwprobe { chain forwardonly { type filter hook forward priority 0; policy drop; } }`.
  2. It reported PASS (`nft default-deny active`) and satisfied an ENFORCE profile requiring the check.
  3. It reached the bound resource, while nika connected to a fresh listener on it (`INBOUND 200`).

**Root cause:** a text search with no notion of which hook or family a chain belongs to.

**Fix applied:**
- The nftables branch reads `nft -j list ruleset` and passes only for an **input-hook base chain of family `inet` or `ip`** whose policy is `drop` or `reject`.
- This also covers iptables-nft's own `ip filter INPUT`.
- Forward/output-only drops and IPv6-only input drops fail; non-JSON output is an Error.
- The iptables (`Chain INPUT (policy DROP)`) and ufw branches are unchanged.

```rust
// BEFORE: try_backend(runner, "nft", &["list", "ruleset"], &["policy drop", "policy reject"], …)
// AFTER:  nft_input_default_deny(runner): nft -j list ruleset → a chain with
//         hook == "input" && family ∈ {inet, ip} && policy ∈ {drop, reject}
```

**Tests:**
- forward/output-only drop fails; ip6-only input drop fails;
- inet/ip input drop or reject passes, also beside permissive chains;
- non-JSON output is an Error.
- 4 mutants killed (hook, family, policy, reject). Client 286 pass.

**Live, fixed client `b1afd95a`:**

| State | Result |
|---|---|
| no firewall | FAIL `nftables present but no default-deny input chain` |
| forward-only drop | **FAIL** (the old client: PASS) |
| inet input chain, policy drop | PASS `nft input chain inet fwtest/input policy drop` |

The enforcement path was verified the same day with the old client:
- ENFORCE denied a failing device;
- a passing report restored access;
- the connector refused a stale-ACL client;
- AUDIT allowed access while recording the reason.

### Fix: the firewall check failed with ufw on an iptables-legacy host (2026-10-29, live E2E run F-1)
**Issue:** on a host whose `iptables` is the legacy backend (here `iptables v1.8.10 (legacy)`), ufw active with
`DEFAULT_INPUT_POLICY="DROP"` was reported `FAIL: nftables present but no default-deny input chain`, so an ENFORCE
profile requiring `linux.firewall.active` refused a protected device.

**Root Cause:** legacy iptables rules (ufw's included) are not in the nftables ruleset. The daemon has
`CAP_NET_ADMIN`, so `nft -j list ruleset` succeeds, and `collect_firewall` returned its FAIL without trying another
backend. The fallbacks couldn't help as written: measured as the daemon's user with only `CAP_NET_ADMIN`,
`iptables -L` fails (`can't open lock file /run/xtables.lock: Permission denied`) and `ufw status` fails
(`You need to be root`). A non-root `ufw status` was also misreported as `ufw inactive`. Before `c7d812cb` the text
match on `policy drop` had passed this host only by accident (Docker's forward chain).

**Fix Applied (`client/src/posture.rs`, `collect_firewall(runner, root)`; user decision: ufw config fallback):**
```rust
// BEFORE: if let Some(c) = nft_input_default_deny(runner).await { return c; }   // nft FAIL was final
// AFTER:
// 1. nft input default-deny → PASS.
// 2. iptables_is_legacy() (`iptables --version` contains "(legacy)", unprivileged): if NOT legacy,
//    nft's answer stands (ufw's rules would be in the nft ruleset).
// 3. legacy: readable `iptables -L -n` decides; an unreadable one (Error) settles nothing.
// 4. `ufw status` decides only when it exits 0 (root); a refusal is not "inactive".
// 5. legacy: ufw_config_default_deny(root): /etc/ufw/ufw.conf ENABLED=yes and /etc/default/ufw
//    DEFAULT_INPUT_POLICY DROP|REJECT → PASS "ufw enabled per /etc/ufw/ufw.conf, default input policy DROP
//    (iptables-legacy: runtime rules not readable)"; ENABLED=no or ACCEPT → FAIL.
// 6. otherwise nft's FAIL, or "no firewall backend found".
```
Known gap (accepted): on a legacy host a manual `iptables -P INPUT ACCEPT` with ufw still enabled in its config is
not seen; `ufw enable` / `ufw disable` keep the config in step.

**Tests (`client/src/posture_tests.rs`):** legacy + ufw enabled (DROP, REJECT) → PASS; disabled or ACCEPT → FAIL;
nf_tables + enabled config + no nft deny → FAIL; config ignored without legacy iptables; legacy without ufw config →
FAIL; readable legacy iptables decides both ways; a refused `ufw status` is not "inactive". 4/4 mutants killed (nft
not authoritative, config without legacy, legacy iptables error returned, ACCEPT policy passing). Client 293 pass.

**Live (2026-10-29, this PC, client `8467ebd98d7c2d61`):** ufw on → `PASS ufw enabled per /etc/ufw/ufw.conf, default
input policy DROP (…)`, profile satisfied, tunnel 200; `sudo ufw disable` → `FAIL ufw disabled (/etc/ufw/ufw.conf)`,
profile unsatisfied, tunnel refused.
